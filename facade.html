Facade Pattern: one button instead of five

A home theater has many parts. Without a facade, the client has to know every part and call them in the right order. With a facade, the client calls one method.

1. Pattern Name and Classification

Name: Facade.

Classification: Object Structural pattern. "Structural" means it is about how classes and objects are put together. "Object" means it works with objects at run time, not with inheritance.

2. Intent

Give one simple interface to a group of complex classes. The facade makes the whole group easier to use.

3. Also Known As

None. The GoF book lists no other name for Facade.

4. Motivation

Think about a home theater. To watch a movie you must dim the lights, lower the screen, switch on the projector, switch on the amplifier, set the volume, and start the player. That is many steps, and the order matters.

If every client does this by itself, every client must know all these classes. The code gets messy and hard to change. So we add one class, HomeTheaterFacade, with a method watchMovie(). The client calls this one method and the facade does all the steps. This is the same as pressing one "Movie mode" button on a remote.

5. Applicability

Use Facade when:

  • You want a simple entry point to a complex system.
  • There are many dependencies between clients and the subsystem classes, and you want to reduce them.
  • You want to organize a system in layers. Each layer gets one facade as its entry point.

6. Structure

This follows the structure used by Refactoring Guru's Facade example. Client talks only to the Facade. A Facade handles one group of related requests (here, watchMovie()); an Additional Facade can be added so the main facade doesn't get cluttered with unrelated features (here, endMovie()). Both facades sit in front of the Complex Subsystem, the set of classes that do the real work. Subsystem classes are unaware of any facade and call each other directly; the client never touches them itself.

7. Participants

  • Facade (HomeTheaterFacade): knows which subsystem classes do which job. It passes client requests to the right objects in the right order.
  • Subsystem classes (Lights, Screen, Projector, Amplifier, Player): do the real work. They do not know about the facade.
  • Client: uses the Facade instead of calling the subsystem classes.

8. Collaborations

  • The client sends a request to the Facade.
  • The Facade forwards it to the correct subsystem objects. It may also translate it into calls the subsystem understands.
  • Clients that use the Facade do not touch the subsystem objects directly.

9. Consequences

Benefits

  • Clients see fewer objects, so the system is easier to use.
  • Loose coupling: subsystem changes do not break clients.
  • Does not block direct access. Clients that need more control can still use subsystem classes.

Drawbacks

  • The facade can grow into a "god class" that knows too much.
  • It adds one more class to maintain.
  • It only shows common features. Rare features may still need direct access.

10. Implementation

  • Reduce coupling further: make the Facade an interface or abstract class. Then different implementations can be swapped without changing clients.
  • Public and private subsystem classes: a subsystem is like a class with its own public and private parts. The Facade is the public interface. Other subsystem classes can be hidden (for example, package-private in Java).
  • Keep the facade thin: it should only call and coordinate. Real business logic stays in the subsystem classes.

11. Sample Code

class Lights    { void dim(int p){ println("Lights dim to "+p+"%"); }
                  void on(){ println("Lights on"); } }
class Screen    { void down(){ println("Screen down"); }
                  void up(){ println("Screen up"); } }
class Projector { void on(){ println("Projector on"); }
                  void off(){ println("Projector off"); } }
class Amplifier { void on(){ println("Amp on"); }
                  void off(){ println("Amp off"); }
                  void setVolume(int v){ println("Volume "+v); } }
class Player    { void play(String m){ println("Playing "+m); }
                  void stop(){ println("Stopped"); } }

class HomeTheaterFacade {
    private Lights l; private Screen s; private Projector p;
    private Amplifier a; private Player pl;

    HomeTheaterFacade(Lights l, Screen s, Projector p,
                      Amplifier a, Player pl) {
        this.l=l; this.s=s; this.p=p; this.a=a; this.pl=pl;
    }
    void watchMovie(String m) {
        l.dim(10); s.down(); p.on();
        a.on(); a.setVolume(7); pl.play(m);
    }
    void endMovie() {
        pl.stop(); a.off(); p.off(); s.up(); l.on();
    }
}

// Client
HomeTheaterFacade theater = new HomeTheaterFacade(
    new Lights(), new Screen(), new Projector(),
    new Amplifier(), new Player());
theater.watchMovie("Inception");   // 1 call, 6 steps done
theater.endMovie();

12. Known Uses

  • Compiler subsystem (GoF example): one Compiler class hides the scanner, parser, and code generator.
  • jQuery: $.ajax() hides the complex XMLHttpRequest details.
  • SLF4J: a simple logging facade over frameworks like Logback and Log4j.
  • Spring JdbcTemplate: hides connection, statement, and cleanup code for database access.

13. Related Patterns

  • Abstract Factory: can be used with Facade to create subsystem objects without exposing their classes.
  • Mediator: also hides complexity, but subsystem objects talk to the mediator. In Facade, the subsystem does not know the facade.
  • Singleton: a Facade is usually needed only once, so it is often a Singleton.
  • Adapter: changes an existing interface to match what the client expects. Facade creates a new, simpler interface.
